What we take from each

  • C is the floor and it ships first. One derivation feeds every tile, the outcome bar and the deployment chips, so the answered count, the rate and the bar can no longer disagree on one screen. Three labels, not six. Answer speed keeps a row and no number. First contact resolution gets nothing, because not even the contact-centre product that publishes a formula page per metric defines it.
  • B is the spine. The threshold is a property of a number, so it lives on the number. The form is two selects, an input and a fixed frequency list, which is Retell's matrix without its cron, and it ships its own all-clear because a breach that never says it is over is what makes people keep checking all afternoon.
  • The breach borrows the diagnosis. A watch knows a number crossed a line; it does not know why. The rules engine on that deployment does, and it already carries a root cause, a suggested fix and a deep link to the control that resolves it. The alert card shows the top cause from the same window and reuses its fixHref. When there is no diagnosis, the card offers See the calls instead of Fix, because a Fix button with nothing behind it is a lie.
  • Silence is a condition. On a count tile the condition list holds No calls at all. It is the only rule in the design that catches a trunk refusing every call, and it is the one thing a threshold on a rate can never do.
  • Delivery stays where delivery lives. Project notifications gains one row, Monitor watches, with its four channels. The watch sheet states where it will go and links there. Two doors for one action would break the standing rule, and the delivery table has been waiting for a row backed by a condition since it was drawn.
  • D goes out as its own small change. Seven real event names, the turn batch named and marked, one payload format row. No destination catalogue.

What we are not doing, and why

  • No Alerts tab, no rules table, no rule names. The second place is the whole failure mode: it needs a metric picker, a picker needs a list, and the list would have to carry numbers we cannot compute. A watch is named by the number it watches, so the reserved-name clash cannot happen.
  • No dashboard builder, no saved views, no card picker. The screen has to be right before it is arrangeable, and the control that would make a builder worth having, the group-by, cannot be wired.
  • No group-by control. It needs labels written when the agent joins the channel, and nothing writes them.
  • No sentiment on Monitor. There is no sentiment field in any request, response or callback payload, and live sentiment trends belong to 12, which is locked.
  • No first contact resolution tile, ever, until someone writes the formula.
  • No cron field, no per-watch channel switches, no second refresh interval.
  • No live surface and no operator verb. 12 is locked.
  • No cost anywhere on this surface. The Engine is a flat $0.10 per agent-minute, charged the same on the customer's own key, so nothing here may suggest a threshold or a model choice moves the bill. Spend keeps its one quiet outlink.

The open question, which is not designable without an answer

Who owns the sentence that defines success. Today the headline success number is produced by an LLM prompt the customer types into a box on one phone number, so it means something different on every number and is never comparable across deployments. Until the owner answers brief question 2, the success tile can be drawn two ways and only one of them can be watched: a watch on today's number is a watch on four different sentences, and a breach on it cannot name what broke. The prototype ships the four tiles that do not depend on that answer and leaves the success tile out.

Audit corrections

Three hostile audits read the build plan for this verdict, on locks, on honesty and on buildability. All three refuted it. Their objections were sourced to line numbers and I checked every one against studio_x_2/ and ng-console/. This section is the argument, so the next reader sees what was cut and what was defended.

What the audits killed

KilledWhy it had to go
answer_speed in MetricKeyThe verdict beats direction A by saying a metric picker would have to carry answer speed, which the contract cannot produce, then puts answer speed in its own key union. series: Record<MetricKey, number[]> is total, so the module would have had to manufacture a sparkline for it, and Watch.metricKey would have let a user set a threshold on it. Answer speed is now not a key at all: it is a fifth tile rendered through MetricCard's existing mute prop with the words Requires Engine, no series, no delta and no Watch control.
The three-segment outcome bar and callerHungUpThe Engine carries state: answered | hangup on the list and reason: request | hangup | failed only on the single-call read, so an aggregate cannot split failed out and nothing anywhere says who hung up. The bar is now two segments, Answered and No answer, both counts, summing to the call total, drawn from the two fields the Studio aggregate really returns (totalCalls, totalAnswered). No answer is the live Console's own word (telephony-page.tsx:3049-3069).
The Transfer to human tiletransferredRateTrend is optional on both analytics types and exists only on the Studio backend, and Deployment.metrics in the sandbox carries no transfer count at all. A tile needs a number; inventing one to carry a caveat line is the failure this feature exists to stop.
coverage.noRetention and Agent.optOutOfRetentionThe caveat had no field behind it, and the field was about to be added purely so a line of copy could count something. Coverage is now { counted, total }, which is true from metrics.calls === 0 and needs no new data.
Updated N minutes ago and updatedAtA local re-derive has no ingest time, and /api/telephony/analytics/summary returns no as-of field, so the chip would have read 0 minutes forever and claimed a fetch that never happened. Refresh is still wired to re-derive; it makes no freshness claim.
