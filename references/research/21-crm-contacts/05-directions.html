What we take from each

  • C is the spine. One question, asked once, answered beside the thing that supplies the value: the contact list for batch, Caller context for inbound. The chips in section 3 carry the state and link to the one row that owns it.
  • B is the floor and ships first. A real file picker, a real header parse, a real count, and phone_number as the required column. Coverage stops being a comparison against a five-item constant, which is the only way learning 3’s check can be extended at all.
  • D becomes one row, not a screen. HubSpot lookup sits in the source list with Requires Engine beside it. The field mapping is not drawn, because every field name in it would be invented.
  • E is the second commit. A Writes to column on the outputs table with the three update modes, defaulting to nothing. It draws the boundary now so nobody builds an unbounded POST later.
  • A folds away entirely. Nothing from it survives except learning 2: the phone number is the key of the row, not one of its variables.

Why not A, which is what the ticket asks for

868kykbf7 says “manage contacts, audiences, and cross-session context”, and a Contacts page is the literal reading. It is refused for three reasons, in order of weight. It is a second contact list, which the owner has already called a failed design. Six of its seven columns describe a store the Engine does not expose, so it is a backend specification wearing a UI. And it does not touch the P0 ticket: a Contacts page does not put one value into one inbound greeting. When the Engine ships a contact object, the list block in C is where it lands, because C already keys the row on phone_number.

Why not D as the spine

D is the direction the JTBD sentence describes and it is the one the docs cannot support. Three of four vendors answer inbound context with a customer-hosted webhook and a published budget; only one ships a CRM lookup, and it states a hard regional limit on it. Drawing a HubSpot field picker today means typing field names nobody has published and a latency figure nobody has measured. The row stays, with its real state on it, until that changes.

The open question, not designable without an answer

Whether labels becomes a builder-visible field or stays a hidden field the CRM feature writes. It is listed in reusablePropertyKeys and then removed from configurablePropertyKeys (ng-console/src/lib/convoai/agent-properties.ts:22–24), a shipped decision I am not going to reverse in a wireframe. It is also the only field that carries a record id from the dial into every notification callback. Without it, no call row can name the record it touched, so the JTBD’s last step has nothing to link to and every write in E is unattributable. The read half ships either way; the write half cannot.
