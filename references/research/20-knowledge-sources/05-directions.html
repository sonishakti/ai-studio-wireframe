Knowledge Source Directions

JTBD. When my prices, policies and help pages change every week and my agent is still answering from the PDF I uploaded in June, I want it reading the same pages my customers read, and to keep reading them without me, so a caller never gets last quarter's answer in a confident voice.

Where it landsThe builder's knowledge row, SectionRow id="wz-5-kb" at components/wizard/step-build.tsx:68, plus the base sheet it opens and the Test rail's transcript. Resources › Knowledge keeps its grid.

A fails the audit. It answers no rainy scenario outright, and it makes four worse. Rainy 3 gets a login field for a crawl that cannot log in, rainy 4 gets a mint-210-chunks report on an empty crawl, and rainy 23 gets a Refresh every select with no last-run stamp anywhere to prove it ever fired. It serves exactly the happy path: paste a URL, get a base. That is the whole of it, and the whole of it is why it is refused.

Three scenarios are answered by nobody, and stay open on purpose elsewhere. 15 (feature-flag skew between teammates) is a Console flag question, not a knowledge question. 22 (a hand edit thrown away) has no edit to throw away, because neither repo lets a document be edited. 26 (a source nothing reads) needs knowledge_retrieval_completed in production before a last-answered date can be true, and drawing one from test data would be a number we cannot compute. 12 is partial everywhere: the Answering mark shows which base answers now, and there is still no lock, no draft and no last-writer notice.

Verdict

B, with C's Answering mark and D's receipt grafted on.

A knowledge base is a container, and files and sites are sources inside it. That single decision is what lets a crawl, a schedule, a freshness stamp and a page ledger exist at all, because each of them is a property of a source and none of them is a property of a base. It is also the shape both crawling vendors shipped, so it is adopted rather than invented.

C is grafted because it is not optional. Attach takes a list, the Engine payload takes one id, and today the second base renders identically to the first and is never queried. A perfect source list on a base nothing reads is the most expensive failure this feature can ship, and the fix is one badge, one line and one menu item.

D is grafted because learning 4 will not let the two dials ship alone. A threshold with no chunk view is a dial that changes an invisible number. With the receipt, the loop closes in one screen: no chunks means raise the count or lower the threshold, chunks present and ignored means the prompt, and the prompt is not this feature's to fix.

What we are not doing. No schedule picker: the interval is a sentence, "Agora reads the site again every seven days", because no vendor in the set exposes one and inventing the market's only interval dial is not a differentiator, it is a support ticket. No login field on a crawl: private pages reach an agent through a connected account, which is feature 19's job, and the crawl says "Public pages only" instead of pretending. No fifth source kind: a crawl fills a base. No knowledge-base detail page: E is the right shape for the quarter after run history is plural, and today it would add a second knowledge surface to an IA tension the owner has ruled open. No Couchbase-branded door: Wave 1 settled that, and the generic provider form already carries it.

The open question, not designable without an answer. Does the Engine take a list of knowledge bases, a kb_ids beside today's single kb_id? Everything about the second row turns on it. If the answer is one, "Attached, not read" is a permanent state and the Answering mark is the feature, and the honest next move is to stop letting a second base attach quietly at all. If the answer is many, the knowledge row becomes an ordered list, eligibility rules apply, and the receipt has to name which base each chunk came from, not just which page. The row cannot be drawn twice, so it waits on one word from Engine.
