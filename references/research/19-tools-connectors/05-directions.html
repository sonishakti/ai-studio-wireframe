What the audit says out loud

A fails. It answers the happy path and one rainy scenario. Twenty of the twenty-eight rows are left exactly where the Before found them, and two of them get worse, because A ports the five-method picker and the second MCP door along with the layout. A direction that only answers the happy path fails the audit, and this is that direction.

D fails as a spine and is right as a graft. It is the only column with a Y on rainy 4, and it has an N on every scenario a user meets before a tool exists. It also cannot ship: the per-tool result it renders is undocumented on the join contract.

Rainy 20 has no Y in any column, and should not have one. When a third-party MCP vendor's own meter empties, nothing on the Agora side moves: the Engine is a flat $0.10 per agent-minute either way. The tool goes to Failing and the user reads the raw body. Drawing anything more here would be inventing a bill we do not send.

Verdict

C. One Tools row, built from the ResourceField two rows above it, and a last result on every tool, every connector and every MCP server.

The row that names this feature becomes the object it names. That is defect 1 and defect 2 in one change, and it costs a rewrite of 45 lines into a component that already exists. Then the create form ends where the job actually ends: a green 200 with the customer's own JSON under it. That is the market's whitespace, our server already answers it, and it converts the proposed tool_verified event from a wish into a hook on a real button.

What I am not doing, and why. Not a marketplace. The server refuses every provider but HubSpot, Retell's eleven is the ceiling among four vendors, ElevenLabs advertises over 400 behind one native connector, and three of the four route the long tail through a single MCP URL. A grid of one live card and five placards is a roadmap dressed as a catalog, so the Connectors tab leads with Add your own, keeps HubSpot as the one card, and drops the four that today complete an authorize dialog the server would reject. Not a hosted code tool. execution.mode has one value and server is required, so there is nothing to run customer code on; it gets a named row, visibly disabled, with the reason on it. Not a schema library. Direction E is the right shape for 868khqaqj and it is built on the object the JTBD puts in 10 · Session & call logs, so it waits for the owner to settle whose feature it is.

The open question, not designable without an answer. Does Studio set advanced_features.enable_tools when an agent has at least one tool attached, or does the customer have to set it? The flag defaults to false, and the contract says tools are then validated and not invoked. If Studio sets it, no control belongs on this screen at all, and the design ships as drawn. If it does not, then a tool can pass its test, attach cleanly, show Working, and never fire, and the row needs a state that says so before the call, not after it. The prototype ships the first answer and adds advanced_features to the Custom config drawer so the flag is at least visible, which is the honest minimum while the question is open.

What is kept against the audits, and why

  • The fourth ResourceField, labelled Tools. One audit offered to keep "Tools & connectors" so that no name moved. Kept: the row holds tools now, and defect 12 is answered by moving all six names in one commit, which the plan does.
  • The check itself. One audit would cut it wherever a prober is missing. It is missing for connectors and cut there. It is documented for custom tools (POST /custom-tools/{toolId}/test) and for MCP servers (GET /mcp/{id}/status), so it stays on both, which is learning 2's whitespace and the hook the proposed tool_verified event needs.
  • The ceiling footer. Read as fabricated, but only its connector addend was. 32 is Engine-enforced, and a number the user sees before spending it is the answer to rainy 7.
  • Hosted code as a visibly disabled row. No audit killed the position, only its typing. Learning 5 says state it rather than leave a blank, and the live Console already states a stack refusal this way.
  • The realtime line, verbatim. "Realtime agents can use MCP servers only." The sandbox has two pipelines, so the shortened sentence is true here. It must not be copied onto a surface that grows a default-LLM path.
  • Dropping the four connectors that complete an authorize dialog the server refuses, and the one placard. Learning 3, unchallenged.

One departure from this document

ToolCreateForm does not live inside step-build.tsx beside its two siblings, as the prototype plan above says. It lives in components/wizard/tool-create-form.tsx and both surfaces import it from there. The reason is scope, not taste: nine features land in one app through one integrator, and step-build.tsx is already the most-edited file in this plan. The property the sibling comment at integrations/page.tsx :21-23 actually asserts, that Resources and the builder create the same record through the same component, is kept.

The owner question, restated

Unchanged and still unanswered: does Studio set advanced_features.enable_tools when an agent holds a tool? The design no longer depends on the answer, because no state on screen claims the agent called anything. If the answer is that Studio does not set it, the row needs a fourth state before the call, and that is a follow-up, not a blocker. The second question, whether 868khqaqj ships here or moves to 10 · Session & call logs, is assumed to move, and direction E is the design if it stays.
