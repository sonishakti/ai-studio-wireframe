Recommendation

Take A as the base and borrow two pieces

A is the only concept that puts stable content, type-specific content and monitoring in three separate places the Console already knows how to show. It answers asks 3, 5, 6 and 16 with tabs, a pattern the Console already uses (ADR 0006), and a new type only adds a tab name. It also keeps the reusable setup in plain sight, which E and D do not.

  • From C: show what each type will ask for on the create cards. It makes the consequence of the choice visible before it is made.
  • From E: switch the model cards to the comparison table once there are more than three tiers.
  • Fallback: B, if engineering wants the least change from the builder shipped on 24 September. Choosing A replaces ADR 0017's section rail and needs a new ADR.
  • Counter-metric: in A the test call is one click away in a sheet. If time to the first test call rises, dock the test panel on the Agent tab from wide screens, as D does.

Open decisions

What the team needs to settle next

  1. Naming a run. The UI says Run, the API says campaign and the docs say batch call. Proposal: the type is “Batch calls”, each execution is a “Run”, and the docs describe a campaign as one run of a batch agent.
  2. Data for the performance view. Session summary, turns and transcripts are deferred past the October launch, and the session list cannot filter by agent. Launch needs a per-agent aggregate endpoint, or the view shows counts only.
  3. Knowledge bases. They are not in the v3 spec. Confirm whether they ship with v3 or the list shows MCP servers and tools only.
  4. The Balanced tier. Confirm its model, or ship two tiers. Every control shape works with two.
  5. Publish and versions. The v3 API has no draft, publish or version. The concepts show Draft until the first run, number or code step. Confirm whether Studio keeps a Publish step.
  6. One type per agent. The API lets one agent back a number and a campaign at once. Studio enforces the rule that a batch agent never takes inbound calls.
