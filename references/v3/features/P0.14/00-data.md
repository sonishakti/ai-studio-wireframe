## What a new account lacks

Everything but the presets: no agent, no number, no run, no session. On a brand-new account nothing in this row renders until an agent has a deployment: the footer keeps P0.4's plain reason slot, the header has no change line, Overview has no Recent sessions block. The flow therefore starts on the demo account's live inbound agent. Empty first holds at every later step too: the since view opens empty right after the save, and the door shows only once a change time exists.

The v3 API has **no draft, no publish step, no version list and no revert**: `PATCH /agents/{id}` is the only write and it is what the next session gets. `updated_at` moves on every write, label-only writes included (retention, deployment type), so it cannot tell a config change from a label change; P1.1 already names the Studio label `studio_config_changed_at` as the change time and `updated_at` as its fallback. There is **no earlier value anywhere in the API** after a save lands: the only place the previous greeting exists is the form's baseline in Sam's browser at the moment of Save. The row keeps that baseline as `before this change` beside `lastSave`, in the browser until the account-level Studio store ships (the same home P0.13 named for the test registry), and says so in words. A hand revert is Sam retyping those values and saving; agent versions stay an API ask.

Sessions since the change need two things the API only half gives: `started_after` exists, the agent filter does not (G4, G12; the list row's `agent_id` is 32 lowercase hex, decision 5). Design mode reads `agent.sessions` with `startedAtIso`; the port shows the gap sentence until sessions link to agents (P1.3.b's words).
