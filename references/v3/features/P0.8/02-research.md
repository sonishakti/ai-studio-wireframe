# P0.8 · Confirm the agent is ready — research

## Rule 0, data first

**a. Does a new logged-in account show the data this flow needs?** Partly. A brand-new draft agent with a deployment type already carries everything the *happy* path's readiness list needs to check honestly (no test heard yet, no prompt written, no number/list connected) — every gap the list would name is real, not fabricated. But the prototype has no agent in a **partial**-readiness state (one gap fixed, one still open) — see Gaps §4 — so today's fixtures can show "nothing done" and "already live," never the in-between moment P0.8.b actually describes.

**b. Where it exists outside our accounts:** ElevenLabs' own product, on the persistent research Chrome profile — already signed in from an earlier session (no new sign-in performed), so its Settings → Advanced → Privacy panel was captured live. Vapi's and Retell's dashboards redirected the same profile to their own login screens this session; per rule, this stopped there and both stayed desk/docs-only, same as the PRD row's own note. Vapi and ElevenLabs public docs (fetched fresh this session to confirm and extend the desk note). Retell's and LiveKit's existing shots (`v3/02-research/monitoring/shots/`, `competitors/product/`) were reused, not re-captured. Refero (`refero_search_screens`) surfaced no authenticated voice-AI go-live screen for any of the four vendors, but did surface Stripe's own payments-activation review step — used as the indirect "go-live checklist" reference the brief asks for. This repo's own desk note, `v3/02-research/batch-retention-experiments.md` §2, was read first and is cited throughout.

**c. What must exist in our own fixtures:** (i) a deployment-typed agent with *some* readiness items done and one still open, to screenshot P0.8.b's "Go live is still allowed" state; (ii) `data_policy` (or an equivalent field) on `Number` and `Campaign` — it does not exist in the v3 API today (confirmed again against `references/api/v3/`; only `SessionCreate` carries it), so P0.8's retention picker has no field to write to yet.

## Per-vendor copy / avoid

**Vapi** — copy: HIPAA is documented as strictly organisation-wide, "applies to every assistant in your organisation, with no per-assistant exception" — Agora's per-Number/Campaign retention ask sits at a finer grain than Vapi's own compliance control, worth stating as a differentiator. avoid: nothing observable in product this pass (dashboard login-gated); no UI to avoid, only the docs' own account-level framing to not copy if Agora wants per-deployment control.

**Retell** — copy: names the strictest tier in plain words the user reads at rest, "Basic Attributes Only — store only metadata (no transcripts/recordings/logs)" — good precedent for how Agora's own "none" retention option should read. avoid: buries the whole privacy control inside "Security & Fallback Settings," a title that reads like connectivity failover, not data policy — don't fold retention into an unrelated settings group.

**ElevenLabs** — copy: splits retention into three independently-toggled controls (kill switch, audio-only toggle, numeric day count) rather than one binary — richer than assumed, and the right reference if Agora's own "30 days or none" ever needs a third state. avoid: the documented batch-calling incompatibility for Zero Retention Mode is invisible at the point of toggling it on in the product itself — Agora's combined Number + Campaign retention control should surface that kind of conflict inline, not leave it to docs only.

**LiveKit** — copy: the disabled-observability empty state — one sentence, one button, no chrome — matches Agora's own empty-first rule and is a fair model for readiness's own "nothing checked yet" moment. avoid: every control here is project-wide; there is no per-agent or per-deployment retention concept in LiveKit to borrow the *scope* from, only the *empty-state tone*.

**Stripe (indirect)** — copy: a flagged card states the reason in one line, shows exactly one fix action, and a card with nothing wrong shows no colour or checkmark at all — matches Agora's own "no green validation" rule already in force. avoid: Stripe blocks forward progress entirely on a missing required step (a hard gate across a 5-step wizard); P0.8.b explicitly wants the opposite — Go live stays available with the gap merely named — so the blocking half of Stripe's pattern is not a fit.

## Gaps

1. **No direct competitor (Vapi, Retell, ElevenLabs, LiveKit) has any pre-publish or go-live readiness gate.** Going live is either instant (ElevenLabs' single "Publish" button, Retell/Vapi autosave) or is simply the first outbound run (LiveKit deploy). P0.8's readiness list (heard test + prompt + number/list, one fix link each) has no vendor UI to copy or avoid from directly — Stripe's activation review (shot 9) was used instead, as the brief anticipated.
2. **Vapi's and Retell's dashboards were login-gated on the persistent research profile this session** (`dashboard.vapi.ai` → `/login`, `dashboard.retellai.com` → Auth0 login) — never signed in, per rule. Only ElevenLabs' session on that profile was already authenticated, so only ElevenLabs was upgraded from desk-only to a live product shot this pass; Vapi's HIPAA setting and Retell's own toggle remain desk/docs evidence, same as the PRD row's own note going in.
3. **`data_policy` still does not exist on `Number` or `Campaign`** in the v3 API (checked again against `references/api/v3/`; only `SessionCreate` carries it, unchanged from the PRD row's own `more.api` note). Every vendor's own retention control is a standing account/agent setting, never bound to one Number or one Campaign — Agora would be first to scope retention that granularly. This is a product decision for the owner (already flagged in the row as open), not a research gap.
4. **No fixture exists for a "partial readiness" agent** (one item done, one still open). Every seeded agent is either fully Draft with zero deployment (`agent_survey`) or fully Live with an existing deployment and no readiness section ever shown (`agent_frontdesk`, `agent_payments`). Design/Build needs a new state to screenshot both P0.8.a's close-to-ready happy step and P0.8.b's "Go live still allowed, one gap named" rainy step.
5. **No reference anywhere in reach — including Stripe — shows a "still allowed to proceed with a named gap" pattern.** Every checklist found (Stripe, the Fernand/TidyCal onboarding checklists surfaced incidentally by Refero) blocks or nags until the item is done; P0.8.b's softer behaviour (Go live stays enabled, the gap is just named) is original design work with no precedent to lean on.
