# P0.15 · Retire an agent — Research

## Rule 0, data first
(a) A brand-new Studio account shows none of this: with zero agents there is nothing to retire, so the flow only exists once at least one agent is live and something (a number, a run) points at it. The happy path and every rainy path here are gated on fixture state, not on anything a new account could produce itself.

(b) It exists partially outside our accounts. Vapi, Retell and ElevenLabs all publish their delete-assistant/agent API reference pages (no sign-in needed), and Retell's public community forum has several live threads about agent/number deletion going wrong — direct evidence, not inference. Refero indexes no voice-agent vendor's delete-agent screen at all (checked `delete AI agent assistant confirmation dialog`, `delete voice assistant agent blocked in use warning dependencies` — zero hits on Vapi/Retell/ElevenLabs/LiveKit); the closest precedent there is generic dev-tool "danger zone" deletes (GitHub, Doppler, Enode, Maze, Replo, Hashnode) plus Vercel's own docs for the indirect pick this row asked for. Our own prototype already has two agents that carry a number today — `agent_payments` (number + a running batch run) and `agent_frontdesk` (number only) — captured this session as the "before" state.

(c) Fixtures the design phase will need: keep `agent_payments`'s number + running run pair (already in `data.ts`) so the confirm sheet's "every number and run" list has real rows to show; add or reuse a second agent with zero numbers/runs so the plain "type the name and delete" happy path (nothing blocked) has a fixture too — `agent_tutor` or `agent_realtime` (code type, no numbers/runs in the seed data) already qualify. There is no Secret Set object anywhere in `data.ts` yet, so rainy P0.15.d ("the agent's secret sets are used by no other agent") has no fixture to render real-looking data from until Secret Set is modeled — flagged under Gaps and already tracked in the row's `more.api`.

## Vendor status

| Vendor | Status | Sources |
|---|---|---|
| Vapi | Partial | Docs (`vapi-01` reference page, community post). `DELETE /assistant/{id}` blocks only on `assistant_pinned` (a parent/child assistant relationship, 409) — nothing about phone numbers, calls or campaigns. Vapi's own docs state a scheduled call re-fetches its Assistant, Phone Number and Customer Number at call time, so "if you delete your saved assistant, the call will fail" — confirmed silent, after-the-fact breakage, not a block. |
| Retell | Partial | Docs (`retell-01`) + three community threads. `DELETE /delete-agent/{agent_id}` takes only the id, no dependency check documented. Community evidence goes further: users report there is *no UI way at all* to unassign an agent from a number any more (staff called it "a known workflow issue"; workaround is to assign a blank placeholder agent instead), a separate case where the phone-number sidebar and the Agents sidebar disagree about whether an agent is still attached (staff confirmed a bug, unresolved), and a third where deleting/opening specific agents threw a persistent error requiring backend intervention. Retell's dependency tracking between agent and number is demonstrably unreliable, not just silent. |
| ElevenLabs | Partial | Docs + product (logged-in, `elevenlabs-01`). `DELETE /v1/convai/agents/{agent_id}` documents a plain 200 → `{}` success and 422 validation errors only, no mention of phone numbers or conversations; the product matches the docs exactly — the agent row's **···** menu sits **Delete agent** directly under **Archive agent**, in red, with no submenu, no confirm step visible before the click, and no count or mention of what uses the agent anywhere in the menu. |
| GitHub (indirect, per this row's brief) | Done for this row's angle | Refero screen (`refero-github-01`, real product screenshot, package settings Danger Zone). "Delete this package" sits in a plain red-bordered Danger Zone box with one line of consequence copy ("it can't be downloaded by users and processes") and a single confirm button — no re-type-the-name gate, no list of what currently depends on the package. |
| Vercel (indirect, per this row's brief) | Partial | Docs (`vercel-01`, REST + dashboard docs, no sign-in). The dashboard delete dialog requires typing the exact project name to confirm, and its copy names *categories* of what goes with it — "deleting your project will also delete the deployments, domains, environment variables, and settings within it" — but this is a static warning line, not a live enumeration of the actual domains/deployments attached, and the REST `DELETE /v9/projects/{idOrName}` reference documents a bare 204/400/401/403 plus an unexplained 409 ("No description") with no public doc of what triggers it. |

No vendor "lists every user of the thing before deleting it" the way this row's happy path proposes: GitHub and ElevenLabs are fully silent; Vapi and Retell are silent at the API layer and broken/confusing at the UI layer for the one relationship (agent ↔ number) this JTBD cares about; Vercel is the closest anyone gets, and it only names categories, never the actual attached items.

## Copy / avoid, per vendor

**Vapi** — Copy: nothing to port — its only dependency check (`assistant_pinned`) is a different relationship (assistant-of-assistant) than the one this row needs (agent-of-number/run). Avoid: shipping a delete that quietly breaks a *future scheduled* call the way Vapi's own docs admit theirs does; P0.15's block-first approach (rainy .b/.c) is a direct answer to this exact failure mode.

**Retell** — Copy: nothing to port from the delete flow itself. Avoid two things: (1) removing the "unassign agent from a number" affordance from the UI entirely, which is the specific complaint in the community thread and forces a support ticket for something that should be self-serve — P0.15's confirm must give Sam a door to re-point the number himself; (2) letting the number↔agent attachment state drift out of sync between two views of the same data (the sidebar mismatch bug) — whatever Studio uses to answer "does a number point at this agent" must be the single source both the agent page and the number page read from.

**ElevenLabs** — Copy: nothing to port; the delete endpoint is a clean, minimal example of exactly the anti-pattern this row exists to avoid (silent, unconditional, no dependent-resource awareness). Avoid: shipping DELETE as a single irreversible call with no pre-check, full stop.

**GitHub (indirect)** — Copy: the Danger Zone visual pattern itself (isolated, clearly red-bordered, one sentence of consequence, nothing else competing for attention on the row) is a clean model for how *little* chrome a destructive action needs when it has nothing to warn about. Avoid: GitHub can afford total silence here because a deleted package has no live traffic pointing at it the instant it disappears; an agent with a number or a running batch run is not in that category, so porting the *box style* without porting the *silence* would recreate Vapi's "call fails later" failure.

**Vercel (indirect)** — Copy: naming the categories of what gets swept away ("deployments, domains, environment variables, and settings") right inside the confirm dialog, not in a separate doc page, is the best precedent found for setting expectations before the type-to-confirm step — P0.15's confirm should do this by *listing the actual numbers and runs*, one step further than Vercel's generic category line. Avoid: an undocumented 409 at the API layer with no stated cause is exactly the kind of unexplained block Studio's `agent_delete_blocked {numberCount, runCount}` event (already in this row's `kpi.events`) is meant to prevent — the reason a delete is blocked must always be visible to Sam, never a bare error code.

## Gaps
- No vendor researched — direct or indirect — combines type-to-confirm with a live, itemized list of what currently depends on the thing being deleted; P0.15's proposed confirm (list every number and run, with a door to re-point or stop each) has no full external precedent to copy wholesale, only partial patterns to combine (Vercel's category warning + Doppler/Enode's type-to-confirm + a dependency list none of them show).
- Retell's own dependency tracking between an agent and a number is documented as unreliable by its own support team (sidebar mismatch bug, still open as of the source thread) — worth a note in the build spec that Studio's equivalent check must be server-verified, not just read from whatever the UI last cached.
- No fixture for Secret Set exists in `data.ts` yet, so rainy P0.15.d cannot be screenshotted with real-looking data until Secret Set is modeled in the prototype (tracked in the row's `more.api` as "no knowledge base or tier in spec" territory — Secret Set specifically is absent from fixtures, not from the v3 API).
- Rainy P0.15.e ("the team's own code still starts sessions with this agent") has no vendor UI precedent anywhere researched — no vendor's dashboard can see code-level references any more than Studio can, so this is copy-only work (an honest disclaimer), not a pattern to port.
- Whether the v3 API actually refuses `DELETE /agents/{id}` while a number or run references it is unconfirmed (per this row's `more.api`); Vercel's undocumented 409 is the only hint anywhere researched that an API-level block is even a common shape, and it comes with no public explanation of its trigger either.
