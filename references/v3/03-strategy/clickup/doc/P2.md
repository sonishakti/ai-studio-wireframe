# P2 Monitoring · Sessions

**Job:** Find out what happened in a session and why
**Situation:** A ticket, a number, a time or a hunch points at one session or a set of sessions.
**Sam wants to:** get to the right session and see what happened and why
**So that:** the cause is fixed once and the proof can be shared

**Done looks like:** Sam gets from any clue to the right session or run, explains what happened, and knows what to change.

**Goal:** Median time to the right session under 60 seconds.

## P2.1 · Spot sessions that went wrong
ClickUp card: https://app.clickup.com/t/868m9wgfk · design ETA Sat 3 Oct · lock ETA Mon 5 Oct

### Job to be done (Sam, a developer)
**Job:** Spot sessions that went wrong · job map: Locate
**Situation:** Without a specific clue, Sam spots which recent sessions went wrong.
**Sam wants to:** see which recent sessions went wrong
**So that:** the worst one gets opened first
**Part of P2 Monitoring · Sessions:** Find out what happened in a session and why

#### P2.1.a Happy path: what Sam does
1. Sam opens Sessions, or the sessions block on an agent, a run, a number or an error group; every one shows the same session list.
2. The list starts at the last 7 days, all statuses, newest first; sessions Studio started carry a Test tag. Sam filters by status to bring failed sessions up.
3. Each row shows start, agent (a link only when an id proves it, else 'Agent not linked' with the name as text), status, then deployment type, direction, transport, duration, cost and error-group tag once the API returns them; tags Test, Ephemeral, Zero retention, Retention unknown.
4. Sam clicks a row and the session opens in a panel over the list (?session=&in=).
5. The up and down keys move to the next session; Esc closes the panel and the list is exactly as Sam left it.

#### Rainy paths: when it goes wrong
*   **P2.1.b** The agent was deleted: The row keeps the agent name as text, with no link.
*   **P2.1.c** No id proves which agent ran the session: The row reads 'Agent not linked' with the name as text; never matched by name.
*   **P2.1.d** The API cannot filter the scope Sam came from: The list filters over loaded pages and says 'partial: first N pages'.
*   **P2.1.e** Nothing in the range: The empty state names the filter that emptied the list, with one-click clear or widen.
*   **P2.1.f** The session is still running: Duration counts up and cost reads pending.
*   **P2.1.g** The session source is down or the network drops: An error with retry; range and filters are kept.
*   **P2.1.h** Retention or origin not returned (G5): The row reads Retention unknown, never Zero retention; ephemeral sessions list like any other.
*   **P2.1.i** Tests crowd out production sessions: Every Studio-started session carries a Test tag, and a Production view is one click away.
*   **P2.1.j** Sam asks for a range past the lookback limit: Presets stop at 30 days until the limit is known; older ranges say 'Older than 30 days, not available'.
*   **P2.1.k** There are no sessions yet: The first-run state says why and offers Talk to agent and Go live (P2.7, P1.8).

### Goal (KPI)
**Median time to the session under 60 seconds, 30 percent faster than the current Console.**
*   Metric: Time to the session
*   Target: Median ≤ 60 s, and ≥ 30 % faster than the current two history pages in a moderated 5-owner task
*   How we measure: history_opened to session_opened, then link_copied, session_downloaded, talk_to_agent_started or agent_updated within 2 min, in the same visit (visitId, 30 min inactivity); median of history_opened to that session_opened over visits that reach it; split by entryPoint and scope
*   Counter-metric: Misses (session_opened, then left in < 5 s) ≤ 20 %
*   Assumption: One reused session list beats the two current history pages. The average Sam arrives and scans about 20 rows before opening one; kill the shared list if the task is not ≥ 30 % faster.

## P2.2 · Get from a clue to the session
ClickUp card: https://app.clickup.com/t/868m9wggy · design ETA Sat 3 Oct · lock ETA Mon 5 Oct

### Job to be done (Sam, a developer)
**Job:** Get from a clue to the session · job map: Locate
**Situation:** With a clue in hand, such as a ticket, a customer or a time, Sam gets to the one session the clue points to.
**Sam wants to:** paste the session id from a support ticket and land on that session
**So that:** the ticket gets an answer in minutes
**Part of P2 Monitoring · Sessions:** Find out what happened in a session and why

#### P2.2.a Happy path: what Sam does
1. Sam pastes a session id into search and the session opens directly.
2. Or Sam types an RTC channel name and the list filters to its sessions.
3. Sam adds facet chips with no counts: status and env first; agent, run, deployment type, direction, transport, origin, retention, number, contact and error group once the API filters them.
4. Keys follow the P1.10 table, so the URL carries every filter.
5. Sam saves the set as a view; a Production view ships beside the default all-origins scope.

#### Rainy paths: when it goes wrong
*   **P2.2.b** No results: The empty state names the filter that emptied the list, with one-click clear.
*   **P2.2.c** The id is not in this project: 'No session with this id in this project', with the query kept.
*   **P2.2.d** The API cannot apply a facet: The list filters over loaded pages with a partial notice.
*   **P2.2.e** The query is slow: Skeleton rows, with the previous results kept until new ones arrive.
*   **P2.2.f** A facet has no data behind it yet (G12, G5): The chip shows disabled with one line on why, never an empty result.
*   **P2.2.g** Sam pastes an agent id or a run id instead of a session id: Search says what kind of id it is and offers that agent or run.
*   **P2.2.h** A saved view names a deleted agent or run: The view opens with that chip marked deleted and every other filter kept.
*   **P2.2.i** The session source is down: An error with retry; query and facets are kept.

### Goal (KPI)
**6 in 10 searches or filters reach the session within 2 minutes.**
*   Metric: Filtered find rate
*   Target: ≥ 60 %
*   How we measure: search_submitted or history_filter_changed to session_opened in the same visit ≤ 2 min, share of visits with a search or filter
*   Counter-metric: Filters cleared within 10 s ≤ 15 %
*   Assumption: Id and RTC channel search resolve most clue-led visits: the average Sam pastes an id from a ticket rather than browsing. Kill id and channel search if search_submitted {kind: session_id|rtc_channel} is below 30 % of history visits with a search.

## P2.3 · Reconstruct how a session went
ClickUp card: https://app.clickup.com/t/868m9wgj8 · design ETA Sun 4 Oct · lock ETA Tue 6 Oct

### Job to be done (Sam, a developer)
**Job:** Reconstruct how a session went · job map: Execute
**Situation:** Sam reconstructs how the session went, from the first word to how it ended.
**Sam wants to:** know what happened in a failed session and why
**So that:** Sam can tell whether the agent, the number or something else is at fault
**Part of P2 Monitoring · Sessions:** Find out what happened in a session and why

#### P2.3.a Happy path: what Sam does
1. The session opens in a panel over the list, or full page; the header shows status, start, end, duration, cost and Status detail (Session.message).
2. Parent chips name the agent (only when an id proves it), run, number, contact and error groups, plus other error groups in this session; each opens its own view.
3. The recording plays on the shared clock; clicking a transcript line or a turn seeks to it (?t=); Download audio sits beside it.
4. Tabs Transcript, Logs, Latency, Analysis and Events read from one timeline; the transport card shows RTC or telephony detail, with a WhatsApp slot.
5. Sam uses Edit agent or Talk to agent to change and retest; Copy link, Download and Full screen sit beside them.

#### Rainy paths: when it goes wrong
*   **P2.3.b** The session is still processing: 'Arrives within a few minutes of the session ending', quiet auto-refresh, ready blocks render first.
*   **P2.3.c** The session is still running: 'Logs and turns arrive when the session ends'.
*   **P2.3.d** A block is not available in the first release (incl. transcripts for RTC and code sessions): One line says so; never an empty block.
*   **P2.3.e** Content is not stored: Zero retention only when a source says so: metadata plus one line on what is never stored; otherwise Retention unknown.
*   **P2.3.f** No id proves the agent: Agent name as text, no chip link, no Edit agent or Talk to agent.
*   **P2.3.g** The recording link expired, or no recording was made: The block says which of the two.
*   **P2.3.h** Sam's role cannot see content: Metadata only, with 'Your role can see session metadata, not transcripts or logs. Ask a project admin.'
*   **P2.3.i** Sam opens a link without project access: A request-access state with no data.
*   **P2.3.j** The session id does not exist: 'No session with this id in this project', with a door to all sessions.
*   **P2.3.k** The agent changed after this session: The agent chip says the agent was saved after this session, so Sam does not read today's settings as the ones that ran.
*   **P2.3.l** The session failed on a revoked or wrong BYOK key: Status detail names the module, with a door to the secret set that holds the key.

### Goal (KPI)
**3 in 10 failed-session reviews lead to an agent change within a day.**
*   Metric: Change after diagnosis
*   Target: ≥ 30 % of failed-session reviews
*   How we measure: session_reviewed {status: failed} or {surface: error_group} to agent_updated on that agent within 24 h, share
*   Counter-metric: agent_reverted within 24 h ≤ 10 %
*   Assumption: Status detail and parent chips above the transcript raise fixes; the average Sam decides within the first screen whether the agent or something else failed. A/B for 2 weeks; kill if the lift is under 5 points.

*   Counter-metric: No-access landings ≤ 5 %; link_copied {rangeKind: relative} = 0

## P2.5 · Follow and stop a run
ClickUp card: https://app.clickup.com/t/868m9wgmk · design ETA Sun 4 Oct · lock ETA Tue 6 Oct

### Job to be done (Sam, a developer)
**Job:** Follow and stop a run · job map: Monitor
**Situation:** While the agent dials a list, Sam sees whether the run is going well and stops the run before more people get a bad session.
**Sam wants to:** know how a run just started is going
**So that:** Sam can stop the run early if contacts are failing
**Part of P2 Monitoring · Sessions:** Find out what happened in a session and why

#### P2.5.a Happy path: what Sam does
1. Sam opens the agent's Runs tab (/agents/:id/runs) and sees each run with status and a counts bar.
2. The run page (/runs/:runId) shows calling windows, the agent chip, from-number chips and counts.
3. Calling and completed counts open the run's sessions once linked; failed opens contacts and attempts once contacts ship; pending and canceled read 'Not dialled'.
4. Sam pauses, resumes or cancels; Run again opens a new run prefilled with the same contact list.
5. The run's sessions show in the shared list, scoped 'Run: <name>'.

#### Rainy paths: when it goes wrong
*   **P2.5.b** Sam cancels a run: The confirm names how many pending contacts will not be dialled.
*   **P2.5.c** The run failed: Code, provider and message, with Run again and a link to the error group.
*   **P2.5.d** The run is paused with no reason given: Reads 'Paused' without a reason until the API adds one.
*   **P2.5.e** Sessions cannot be linked to the run yet: Counts show; segments are disabled with the reason.
*   **P2.5.f** The agent was deleted: Cached name, or 'Deleted agent (agent_…)'.
*   **P2.5.g** The run is scheduled but not started, or outside its calling window: The header shows the next calling window; no sessions yet.
*   **P2.5.h** Free minutes run out mid-run: The minutes banner says the account is suspended and dialling stopped; pending contacts stay pending, and Run again works after top-up.
*   **P2.5.i** A failed dial may not create a session: Failed opens contacts and attempts once contacts ship; until then it is disabled with the reason.
*   **P2.5.j** Pause or cancel fails on a network or API error: The control returns to its prior state with the error and a retry.
*   **P2.5.k** Run not found or no access: A not-found state with a link to Agents.

### Goal (KPI)
**6 in 10 bad runs get paused or canceled before half the contacts are dialled.**
*   Metric: Bad runs stopped early
*   Target: ≥ 60 %
*   How we measure: A Studio job polls GET /campaigns counts every 5 min. Bad run: failed / (completed + failed) of 20 % or more at any point before 50 % progress. Numerator: run_status_changed {to: paused|canceled, trigger: user} before progressShare 0.5. Pauses from suspension or the API are excluded. Share of bad runs.
*   Counter-metric: Pauses undone within 5 min ≤ 10 %
*   Assumption: Counts plus pause stop bad runs early; the average Sam checks a new run within its first 10 minutes. Kill below 40 %.
