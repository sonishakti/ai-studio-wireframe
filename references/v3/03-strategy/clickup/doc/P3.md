# P3 v3 mapping

**Job:** Look after what all the team's agents share
**Situation:** Several agents share provider keys, numbers and integrations, set up by hand or from code.
**Sam wants to:** manage what the agents share, by hand or from code
**So that:** a change lands the same way everywhere and nothing breaks silently

**Done looks like:** Every agent, number, secret and integration Sam makes by API opens, changes and saves the same in the Console, under the same names.

**Goal:** All 201 API settings have a Console home or a reason, and 20 of 20 agents save unchanged.

## P3.1 · Replace a provider key without breaking agents
ClickUp card: https://app.clickup.com/t/868m9wgne · design ETA Tue 6 Oct · lock ETA Thu 8 Oct

### Job to be done (Sam, a developer)
**Job:** Replace a provider key without breaking agents · job map: Modify
**Situation:** Across the team's agents, Sam replaces or retires a provider key without breaking any agent that uses that key.
**Sam wants to:** rotate a leaked LLM key
**So that:** every agent keeps answering with the new one
**Part of P3 v3 mapping:** Look after what all the team's agents share

#### P3.1.a Happy path: what Sam does
1. Sam opens Secrets; each set shows its key names, updated date and used by (agents Studio wrote, from labels.studio_secret_sets, and numbers).
2. Sam picks the set and chooses Replace value on the key; the sheet asks for the new value only and reveals nothing.
3. Studio compares key names with the saved set; nothing an agent references is missing, so Save sends PUT.
4. The row shows the new updated date, and Studio offers a test on one agent that uses the set.
5. Sam hears that agent answer; the rotation is done.

#### Rainy paths: when it goes wrong
*   **P3.1.b** Sam deletes a set an agent still uses: The server refuses (409, the detail names one agent in text). Studio lists every agent and number it knows uses the set, adds 'API-created agents may also use it', and keeps the set.
*   **P3.1.c** Sam's replacement drops a key an agent references: PUT swaps the whole set, so Studio diffs key names first and blocks Save until Sam re-points the agent or confirms.
*   **P3.1.d** Sam finds a set Sam never made by hand: Sets the builder made carry the chip 'Created by agent Support desk' from the set name. If that agent is deleted the chip reads 'Agent deleted' and the set stays.
*   **P3.1.e** Someone saved the set while Sam was typing (412 stale ETag): The sheet reloads key names and keeps the values Sam typed; Sam saves again.
*   **P3.1.f** Sam needs to check a stored value: Values are write-only: the row shows key name and updated date, and the only action is Replace value.
*   **P3.1.g** The new key is wrong or revoked: The spec has no key check, so a saved key is not a working key. After Save, Studio offers a test on an agent that uses the set; byok_key_failed names the module that failed.
*   **P3.1.h** Sam has no secret sets yet: One line says sets are made here or when Sam pastes a key in the builder, plus Add secret set.
*   **P3.1.i** The network drops during Save: The sheet keeps key names and typed values and offers Retry. PUT is one request, so the set is either the old one or the new one.

### Goal (KPI)
**Replacing a secret key breaks zero agents.**
*   Metric: Safe secret replace
*   Target: 0 agents broken by a secret replace; API-created agents reported as unknown coverage
*   How we measure: operation_succeeded {secret_set_replace} to session_ended {status failed, errorCode provider_auth} (G2) or byok_key_failed within 24 h on agents in labels.studio_secret_sets for that set, count of agents per replace (secret_replace_broke_agent). Blocked on G2; interim: byok_key_failed in tests only.
*   Counter-metric: Secrets page visits per new agent ≤ 0.2: keys belong in the builder, not a detour here
*   Assumption: A used-by list makes write-only keys safe for Sam to manage. Method: derived check after every PUT. Kill: any broken agent adds a replace confirm step.

## P3.2 · Route every number to an agent
ClickUp card: https://app.clickup.com/t/868m9wgpc · design ETA Wed 7 Oct · lock ETA Fri 9 Oct

### Job to be done (Sam, a developer)
**Job:** Route every number to an agent · job map: Monitor
**Situation:** Sam makes sure every number the team owns reaches the right agent.
**Sam wants to:** check the support number after moving agents around
**So that:** every inbound session reaches the right agent
**Part of P3 v3 mapping:** Look after what all the team's agents share

#### P3.2.a Happy path: what Sam does
1. Sam opens Numbers; each row shows the number, description, inbound agent and the runs that use it as from.
2. Sam chooses Add number and fills SIP protocol, host, port and allowed IPs; the SIP password is saved as a secret reference and never shown.
3. Sam picks the inbound agent and saves; channel_connected (inbound) fires for that agent.
4. The row now names the agent; Sam dials the number and hears it answer.

#### Rainy paths: when it goes wrong
*   **P3.2.b** A number has no agent and no run dials from it: The row warns 'No agent: inbound sessions fail'; a filter pins these rows first.
*   **P3.2.c** Sam points a number another agent holds: A confirm names the agent that loses its inbound deployment before Save.
*   **P3.2.d** Sam deletes a number a scheduled or running run uses: Delete is blocked; the message names the run and links to it.
*   **P3.2.e** The number already exists (409) or the SIP host is wrong: Inline error on that field from ErrorResponse.reason; the other fields keep their values.
*   **P3.2.f** Sam has no numbers yet: One line plus Add number; carrier setup docs are linked because the spec has no number purchase.
*   **P3.2.g** The trunk is down or the SIP login is wrong: The API has no status or trunk health, so the row claims nothing it cannot know. It asks Sam to dial the number and hear the agent (first-week states, P1.8); trunk health is raised as an API ask.
*   **P3.2.h** The secret behind the SIP password was replaced or removed: The row warns and links the secret set (P3.1).
*   **P3.2.i** Sam has hundreds of numbers: The list pages by cursor (GET /numbers) and searches by number, description or agent.

### Goal (KPI)
**No phone number goes more than 7 days without an agent to answer it.**
*   Metric: Unassigned numbers
*   Target: 0 numbers without inbound.agent for > 7 d, excluding numbers used as a run's from number in the last 30 d
*   How we measure: Daily snapshot of GET /numbers stored by Studio (the API has no updated_at). A number counts once it has had no inbound.agent in 7 consecutive snapshots, minus numbers that are a run's transport.from in the last 30 d (number_unassigned_7d, derived). First read on day 8.
*   Counter-metric: Numbers re-pointed within 24 h of Go live ≤ 10 % (number_reassigned; re-points made through the API are not covered)
*   Assumption: Seeing the agent on every row lets Sam catch a dead deployment. Method: compare accounts that open Numbers within 14 d with those that do not. Kill: no difference in unassigned numbers.

## P3.3 · Decide how sessions on numbers end
ClickUp card: https://app.clickup.com/t/868m9wgq5 · design ETA Wed 7 Oct · lock ETA Fri 9 Oct

### Job to be done (Sam, a developer)
**Job:** Decide how sessions on numbers end · job map: Define
**Situation:** Across all the team's numbers, Sam makes sure sessions end cleanly and reach a person when the agent should stop.
**Sam wants to:** the support number to close silent sessions and hand upset callers to a person
**So that:** no session hangs open or dead-ends
**Part of P3 v3 mapping:** Look after what all the team's agents share

#### P3.3.a Happy path: what Sam does
1. Each number row shows a one-line policy summary, for example 'Ends after 10 min or 30 s of silence; transfers to the front desk'.
2. Sam chooses Edit; the same inbound policy sheet as Go live (P0.9) opens.
3. Sam sets max duration and the silence limit in seconds.
4. Sam turns on the end rules needed from four: conversation complete, caller asks to end, fax, another AI assistant answers.
5. Sam adds a transfer number in E.164 with a short description and saves; the row summary updates.

#### Rainy paths: when it goes wrong
*   **P3.3.b** Every rule is off by default in the spec: The sheet pre-fills a recommended set and says which rules stay off.
*   **P3.3.c** Sam thinks in seconds, the API stores milliseconds: Sam types the silence limit in seconds; Studio saves max_silence_duration_ms and names the API field in a tooltip.
*   **P3.3.d** The transfer number is not E.164, or the description passes 1000 characters: Inline error on that field; Save waits.
*   **P3.3.e** Sam changes the policy while sessions are running: The sheet says the change applies to new sessions (API team to confirm).
*   **P3.3.f** A value is out of range: Inline error with the allowed range from the spec, before Save.
*   **P3.3.g** Sam needs the transfer headers or transfer type the current Console had: Not in the spec: the sheet leaves them out, says so once, and they are raised as an API ask.
*   **P3.3.h** The number is only a run's from number: Inbound policy never applies to runs; the sheet says a run's end rules are set on the run.
*   **P3.3.i** Sessions keep hitting the time cap: Once session_ended carries the number (G2), the row shows how many sessions ended at the cap in 7 d and links to them in history.

### Goal (KPI)
**Fewer than 5 in 100 inbound sessions get cut off by the time cap.**
*   Metric: Cut-off inbound sessions
*   Target: ≤ 5 %
*   How we measure: Inbound sessions whose duration ends within 2 s of max_call_duration_seconds, share of inbound sessions per number per week (session_cut_off, derived). Blocked on G2 (session_ended with a number id), G14 and G10 (the policy in force at session time).

*   Assumption: Sam sets the policy once, at Go live: ≥ 80 % of policy saves come from Go live. Method: operation_succeeded {telephony_phone_number_update} by entryPoint (entryPoint is on the allowlist). Kill: above 40 % from Numbers makes Numbers the primary door.

## P3.4 · Reuse integrations across agents
ClickUp card: https://app.clickup.com/t/868m9wgqx · design ETA Wed 7 Oct · lock ETA Fri 9 Oct

### Job to be done (Sam, a developer)
**Job:** Reuse integrations across agents · job map: Prepare
**Situation:** Sam gives several agents the same access to another system and knows which agents a change would affect.
**Sam wants to:** the CRM lookup tool from the support agent on the sales agent too
**So that:** both answer from the same data
**Part of P3 v3 mapping:** Look after what all the team's agents share

#### P3.4.a Happy path: what Sam does
1. Sam opens Integrations; every MCP server and tool found on the project's agents is listed once, grouped by endpoint or URL.
2. Each row shows name, type icon, allowed tools and used by.
3. Sam chooses Add to agent on the CRM tool and picks the sales agent.
4. Studio copies the entry into that agent's Integrations list and asks Sam to re-enter the header values.
5. Sam saves and tests the sales agent; app_connected fires if this is its first integration.

#### Rainy paths: when it goes wrong
*   **P3.4.b** Headers do not come across in the copy: Headers are write-only, so Add to agent asks Sam to re-enter each value, or pick a secret reference once the API confirms $secrets works in headers.
*   **P3.4.c** Sam looks for a knowledge base or HubSpot: Not in the v3 spec: no row ships that cannot save; items from the current Console show read-only with a notice.
*   **P3.4.d** Sam looks for WhatsApp among integrations: WhatsApp leaves this list: it is a future deployment type and transport, never an integration.
*   **P3.4.e** Sam has no integrations yet: The empty state opens the builder's Integrations list.
*   **P3.4.f** Sam changes one copy and expects every agent to change: Each agent holds its own copy; there is no project-level object. The row says a change on one agent stays on that agent and flags agents whose allowed tools or timeout differ.
*   **P3.4.g** An integration fails and the row cannot say so: The API has no health field, so the row shows no status; used by links open each agent's test (journey INT-R).
*   **P3.4.h** The project has many agents and the scan is slow or fails: The page scans GET /agents page by page and fills rows as they load; on a failure it keeps what loaded and offers Retry.

### Goal (KPI)
**3 in 10 accounts with a second agent reuse an MCP server or tool within 30 days.**
*   Metric: Reuse rate
*   Target: ≥ 30 % of accounts reaching a second agent reuse one MCP endpoint or tool URL on 2 or more agents within 30 d. Details: the page's share of reuse events ≥ 15 %.
*   How we measure: Accounts reaching a second agent_created; within 30 d of it, the same MCP endpoint or tool URL is on 2 or more agents (GET /agents scan), share. Page attribution: integration_added {entryPoint: integrations_page}, share of reuse events.
*   Counter-metric: Integrations removed within 24 h ≤ 15 %
*   Assumption: Sam reuses integrations across agents, and the page helps. Method: GET /agents scan at 30 d. Kill: if the page's share of reuse events is below 15 %, retire the page and keep integrations in the builder.

## P3.5 · Switch an agent between code and hand edits
ClickUp card: https://app.clickup.com/t/868m9x4gm · design ETA Thu 8 Oct · lock ETA Mon 12 Oct

### Job to be done (Sam, a developer)
**Job:** Switch an agent between code and hand edits · job map: Modify
**Situation:** Sam sets up an agent from code and adjusts the agent by hand, or the reverse, without losing a setting.
**Sam wants to:** create agents from a script and tune them in the Console
**So that:** neither side resets the other's work
**Part of P3 v3 mapping:** Look after what all the team's agents share

#### P3.5.a Happy path: what Sam does
1. Sam creates an agent with POST /agents from a script.
2. Sam opens it in the builder; every field lands in one home: preset, Advanced, Prompt, Integrations or Deployment.
3. Sam changes the greeting and saves; Studio sends PATCH with only that change.
4. Sam runs GET on the agent; the body matches the script's plus the greeting, nothing else differs.
5. Sam opens the read-only JSON view, which uses API field names, and copies the body back into the script.

#### Rainy paths: when it goes wrong
*   **P3.5.b** A field exists only in the API (inbound lifecycle, greeting audio, session actions inject, speak, interrupt): Each gets a home or sits on the approved API-only list with the reason, shown in the JSON view.
*   **P3.5.c** A current Console control has no API field (SAL, voice formatting, recording toggles, provider fallback): Cut, or raised as an API ask; never kept as a control that cannot save.
*   **P3.5.d** Someone saved the agent first (412 PreconditionFailed): Studio shows both versions and keeps Sam's edits to reapply.
*   **P3.5.e** The API rejects a value (InvalidFieldValue, InvalidModuleParameter): The ErrorResponse reason lands on that field in the builder, never a generic toast.
*   **P3.5.f** An agent made by API uses a value no preset holds: The builder opens on Custom and shows the value as is; it never snaps the agent to a preset.
*   **P3.5.g** An agent made by API has no deployment type label: The builder asks Sam once which deployment type it is and stores it in labels.studio_deployment; it never guesses.
*   **P3.5.h** The spec changes under Sam (3.0.0 still moving): The parity script re-runs per spec version; new fields show in the JSON view until they get a home.
*   **P3.5.i** Sam copies the JSON and worries about keys in it: Secrets show as $secrets.<set>.<key> references; values never appear.

### Goal (KPI)
**All 201 API settings have a Console home or a stated reason why not.**
*   Metric: API parity
*   Target: 100 % of 201 spec leaf fields settable in the Console or on the approved API-only list with a reason; renames only Analysis and run, API word in a tooltip
*   How we measure: Parity script over spec ih7axj9zx 3.0.0: fields with a Console home plus fields on the API-only list, share of 201 leaf fields; re-run per spec version
*   Counter-metric: Advanced panel opened by ≤ 30 % of new agents
*   Assumption: The round trip holds for Sam's agents. Method: 20 fixture agents (every pipeline mode, vendor and tool shape) made by API, opened and saved in Studio, return an identical GET body in 20 of 20, per spec version.
