## Job to be done (Sam, a developer)
**Job:** Get from a clue to the session · job map: Locate
**Umbrella job (P2):** Sam wants to find out what happened in a session, or in a set of sessions, and why.
**Situation:** With a clue in hand, such as a ticket, a customer or a time, Sam gets to the one session it points to.
**Story:** Sam has a session id from a support ticket, so Sam wants to paste it and land on that session.

### P2.2.a Happy path: what Sam does
1. Sam pastes a session id into search and the session opens directly.
2. Or Sam types an RTC channel name and the list filters to its sessions.
3. Sam adds facet chips with no counts: status and env first; agent, run, deployment type, direction, transport, origin, retention, number, contact and error group once the API filters them.
4. Keys follow the P1.10 table, so the URL carries every filter.
5. Sam saves the set as a view; a Production view ships beside the default all-origins scope.

### Rainy paths: when it goes wrong
*   **P2.2.b** No results: The empty state names the filter that emptied the list, with one-click clear.
*   **P2.2.c** The id is not in this project: 'No session with this id in this project', with the query kept.
*   **P2.2.d** The API cannot apply a facet: The list filters over loaded pages with a partial notice.
*   **P2.2.e** The query is slow: Skeleton rows, with the previous results kept until new ones arrive.
*   **P2.2.f** A facet has no data behind it yet (G12, G5): The chip shows disabled with one line on why, never an empty result.
*   **P2.2.g** Sam pastes an agent id or a run id instead of a session id: Search says what kind of id it is and offers that agent or run.
*   **P2.2.h** A saved view names a deleted agent or run: The view opens with that chip marked deleted and every other filter kept.
*   **P2.2.i** The session source is down: An error with retry; query and facets are kept.

## Goal (KPI)
**6 in 10 searches or filters reach the session within 2 minutes.**
*   Metric: Filtered find rate
*   Target: ≥ 60 %
*   How we measure: search_submitted or history_filter_changed to session_opened in the same visit ≤ 2 min, share of visits with a search or filter
*   Counter-metric: Filters cleared within 10 s ≤ 15 %
*   Assumption: Id and RTC channel search resolve most clue-led visits: the average Sam pastes an id from a ticket rather than browsing. Kill id and channel search if search_submitted {kind: session_id|rtc_channel} is below 30 % of history visits with a search.
