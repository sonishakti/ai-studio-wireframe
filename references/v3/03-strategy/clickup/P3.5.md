## Job to be done (Sam, a developer)
**Job:** Switch between code and hand edits · job map stage **Modify** (Sam adjusts without breaking what runs)
**Umbrella job (P3):** Sam wants to look after everything the team's agents share, by hand or from code, and get the same result either way.
**Situation:** Sam sets up an agent from code and adjusts it by hand, or the reverse, without losing a setting.
**Sam wants to:** create agents from a script and tune them in the Console
**So that:** neither side resets the other's work

### P3.5.a Happy path (this is what Sam does)
1. Sam creates an agent with POST /agents from a script.
2. Sam opens it in the builder; every field lands in one home: preset, Advanced, Prompt, Integrations or Deployment.
3. Sam changes the greeting and saves; Studio sends PATCH with only that change.
4. Sam runs GET on the agent; the body matches the script's plus the greeting, nothing else differs.
5. Sam opens the read-only JSON view, which uses API field names, and copies the body back into the script.

### Rainy paths (each needs its own state in the prototype and a frame in Figma)
*   **P3.5.b** A field exists only in the API (inbound lifecycle, greeting audio, session actions inject, speak, interrupt): Each gets a home or sits on the approved API-only list with the reason, shown in the JSON view.
*   **P3.5.c** A current Console control has no API field (SAL, voice formatting, recording toggles, provider fallback): Cut, or raised as an API ask; never kept as a control that cannot save.
*   **P3.5.d** Someone saved the agent first (412 PreconditionFailed): Studio shows both versions and keeps Sam's edits to reapply.
*   **P3.5.e** The API rejects a value (InvalidFieldValue, InvalidModuleParameter): The ErrorResponse reason lands on that field in the builder, never a generic toast.
*   **P3.5.f** An agent made by API uses a value no preset holds: The builder opens on Custom and shows the value as is; it never snaps the agent to a preset.
*   **P3.5.g** An agent made by API has no deployment type label: The builder asks Sam once which deployment type it is and stores it in labels.studio_deployment; it never guesses.
*   **P3.5.h** The spec changes under Sam (3.0.0 still moving): The parity script re-runs per spec version; new fields show in the JSON view until they get a home.
*   **P3.5.i** Sam copies the JSON and worries about keys in it: Secrets show as $secrets.<set>.<key> references; values never appear.

## Goal (KPI)
**In one line:** All 201 API settings have a Console home or a stated reason why not.
*   Metric: API parity
*   Target: 100 % of 201 spec leaf fields settable in the Console or on the approved API-only list with a reason; renames only Analysis and run, API word in a tooltip
*   How we measure: Parity script over spec ih7axj9zx 3.0.0: fields with a Console home plus fields on the API-only list, share of 201 leaf fields; re-run per spec version
*   Counter-metric: Advanced panel opened by ≤ 30 % of new agents
*   Assumption we are testing: The round trip holds for Sam's agents. Method: 20 fixture agents (every pipeline mode, vendor and tool shape) made by API, opened and saved in Studio, return an identical GET body in 20 of 20, per spec version.
