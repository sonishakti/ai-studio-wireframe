Studio v3 Strategy

The Console becomes the same shape as the v3 API: Secret, Agent, Session, with every deployment in the session's transport. This page is the plan for the four workstreams you set (P0 agent flow, P1 agent page, P2 session history, P3 v3 mapping), grounded in both 24 Sep calls, the evening spec, and four research passes.

Launch: mid-October · new Studio + v3 API + SuperNode · US EastBuilt inside the existing Console design systemBranch design/v3
The short version
Close the loop the Console breaks today: build, go live, watch, find the bad call, change, prove it helped.
  • Aggregate on the agent, drill down in history. Vineet was explicit: session history is for finding one call; totals live only on the agent.
  • Optimise the hot path, keep the depth. Two presets plus Custom, one Advanced panel that restores every setting Concept A dropped, then a delight pass with vendor logos.
  • UI equals API. Same entities, same words, field-for-field for Create an agent and Start a session.
  • The research found open squares. No competitor unifies sessions across modalities, renders zero-retention rows, has an ephemeral-session state, or shows which agents use a secret before you delete it.
  • The biggest risk is data, not design. The v3 spec defers session analytics, transcripts and events past launch, and the P1 and P2 designs depend on them. Deciding the day-one data source is the first call to make.

What the research says

Open squares Agora can own

  • One session list across every modality. No competitor documents one.
  • A defined zero-retention row. Competitors document retention mechanics, never what the row shows.
  • An ephemeral, no-agent session state. Every vendor ties sessions to a saved agent.
  • "Used by" before deleting a secret. None of the six secret stores show it.
  • Rerunning the same batch. Every competitor treats a batch as single-level.

Patterns to adopt

  • One filter and time state drives tiles and list, and every tile drills to rows (Datadog, Amplitude, PostHog).
  • field:value search plus a facet panel that mirrors it (Datadog Log Explorer).
  • Errors grouped into issues with counts and affected sessions (Datadog Error Tracking, Sentry).
  • A turn timeline with ASR, LLM and TTS legs beside transcript and scores (Langfuse, Hume session detail on Refero).
  • Preset cards with a logo strip, and Custom opening pre-filled from the default (Vapi's reasoning, ElevenLabs' grouping).
  • Write-only secrets: key immutable, rotate by overwrite (Vercel), environment on the set (Doppler).

"Session" is the right umbrella word for a modality-agnostic product, and "call" is best kept for telephony. "Analysis" matches the Console's existing Call Analysis and the market's direction.

API parity and the spec

A field-level diff of the evening spec against the live Console builder and Concept A, covering Create an agent, Start a session, and the Go live fields on Number and Campaign.

MeasureResult
Spec fields audited144
Covered by the live Console96 (67 %)
Covered by Concept A46 (32 %)
Shown in a UI with no API field25
  • Concept A dropped two thirds of the pipeline. Its Advanced sheet has four switches. The live Console's turn-taking, silence and filler-word controls match the spec almost 1:1, defaults included, so they are the reference for the one Advanced panel.
  • Analysis sits at the wrong level in the live Console. It is configured per number and per campaign, never on the agent, so one agent cannot share one analysis definition. v3 puts structured_output on the agent.
  • No Start a session surface exists. Neither UI has one, so session lifecycle, data retention and RTC transport settings appear nowhere in the Console. For inbound and batch, Go live has to carry them.
  • Legacy names still ship. The live Console writes v2 names (system_messages, greeting_message, endpointing) where v3 says instructions, greeting.text and turn_detection.
  • The UI does things the API cannot. Knowledge base, recording and transcript toggles, SIP transfer headers, provider fallback and selective attention locking have no v3 field. Each needs an API home or a removal decision.
  • Units differ. Ring and silence limits are seconds in the UI and milliseconds in the spec.
  • Avatar is modelled in the Console's data layer but never rendered. It is a ready-to-wire gap.

KPIs

The north star stays Fast-Proven Rate: agents that answer within 15 active minutes and hold a real conversation within 14 days, target 45 %. v3 reports Retained Production Agents beside it, because the per-minute business earns on agents that keep taking calls.

Nothing is instrumented yet. Four things must exist first: a session list with an agent filter and more than 2 hours of history, a session summary with analysis results, the RTM error stream exposed to the Console, and browser events for page opens, filters, shares and talk-to-agent.

Decisions needed from the team

  1. Day-one session data. The spec defers latency, analysis results, transcripts and events. Which source feeds the agent page and session detail at launch: the v2 analytics pipeline, the RTM stream, or an honest empty state?
  2. Error logs. Which RTM log types exist per session, and in what shape (Vineet took this).
  3. Data policy for inbound and batch. Add data_policy to Number.inbound and Campaign, or a project or agent default. Also decide whether zero retention is allowed on batch; ElevenLabs forbids it.
  4. Run or campaign. The API campaign is one run with nothing above it. The recommendation is to call it Campaign in the UI for launch, show several as runs only in the comparison view, and add a grouping entity later.
  5. Secret deletion. Your recap says never; the call says delete and recreate; the spec says only when unreferenced. The proposal is no reveal, with delete allowed only when no agent uses the set, and the using agents listed.
  6. Pricing copy. The call said 5¢ managed, lower with BYOK, not public. Presets show latency and intelligence only until pricing clears.
  7. Knowledge base. Not in the v3 spec. Is it in v3?
  8. Variant pointer. Put agent version, override and ephemeral on every session record before launch, so future A/B and override analytics are a join, not a migration.
