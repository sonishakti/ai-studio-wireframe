How the loop runs

›The loop, from Sam to a KPI read13 stops · 8 gates

Every feature walks the same loop. The sheet is the record; ClickUp is the queue and the team view; Figma is the design of record; the commit is the lock FE pulls.

  • Two dates per row. Design ETA is when the agent delivers for review. Lock ETA is when the row should be Done, two days later on a working day. Every lock lands before Fri 16 Oct.
  • Humans follow the ETAs; the agent follows the queue. The agent runs four times a day and takes the next row that is not done, so it runs ahead of the ETAs. An ETA only turns red when a lock is late.
  • Done locks the design. The Figma section is frozen and the commit is the lock. Later rows never change a locked design unless the change is in their own scope or improves it; then the agent names the locked ids in the review post and you decide.
  • One row, one lock. Each feature ships with its own commit on design/v3 and its own Figma section, so review, FE pull and rollback stay per feature.
  • Redo jumps the queue. Move the task back to in progress and comment change: …; the next run takes it first.
  • Proposed rows (P0.14, P0.15, P1.11) have no dates until you sign them off in ClickUp.
›The agent's day: four runs

One contract, one schedule. At each run the agent applies your verdicts, takes the next job step that is not done, builds only that job (what Sam does, happy path and every rainy state), puts the flow in Figma with screenshots and the rationale, and posts one message. It never marks a row Done.

›Research rules for every agent
Rule 0, data first.Before researching or designing a flow, answer three questions and write them on the row: does a new logged-in account have the data this flow shows? If not, where outside our accounts does it exist (signed-in competitor accounts, vendor docs, Refero, the shots already captured)? And what must be created in our own account (agents, test sessions, forced failures, a run, a number) so the screenshots show real data? Our accounts hold few agents, sessions or failures, so monitoring and session rows always need this.
  1. Existing research first. The row's research table, references/v3/ and references/research/ screenshots, and the Figma research sections. Reuse; never re-capture what exists.
  2. Then MCP tools: Refero screens and flows, vendor docs through fetch and search, our own Figma boards through the Figma connector.
  3. Then the built-in browser for public pages and docs.
  4. Claude in Chrome last, on the signed-in competitor profile, only when context is still missing or a changelog says the vendor shipped something new since the existing shots.
  5. Always 3 direct and 1 indirect competitor. Direct: Vapi, Retell, ElevenLabs. Indirect by topic: LiveKit for infrastructure, Datadog or Sentry for monitoring, Twilio for telephony, Bland for batch.
  6. Research runs on Sonnet or Opus. Fable only for the design verdict and the build.
  7. Empty states are rainy scenarios, not research. Act in the environment to reach the populated state before capturing.

›Design system: change once, update every committed design
  • Tokens live in one place. docs/design/DESIGN.md maps the live design system; the CSS variables in src/styles.css are the source; Figma variables mirror them. A token change re-renders every prototype route on design/v3 and, once the kit is published, every native frame bound to that variable.
  • Frames are built from the kit, never detached. Hero screens use the kit components on page 31:2 with variables bound; a component change in the kit updates every locked section on publish without a re-approval.
  • What needs a re-approval. Token and component changes propagate silently. A structural change to a locked flow goes through the loop again as its own row.
  • One shot, one commit. A design-system change is one commit on design/v3 plus one kit publish, named in the sheet's change log, so FE can pull the token change separately from feature commits.
